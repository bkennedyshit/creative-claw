# GPU Broker VRAM arbitration plugin (v2)

The GPU broker extension implements a five-state state machine arbitrating VRAM between agent inference and user workloads, with polling, ghost-claim detection, lease management, and operator surfaces. Four of the five v1 issues have been addressed: the dead `reload.onConfigChange` field is removed, the hook handler accepts `(_event, _ctx)`, Ollama snapshot fields are `number | null`, and the advisory-only nature of the gate is documented. The fifth (agent-active never exits) was fixed in the gate but introduced a new problem in the warmup path.

**Watch for:** Warmup recalibration is now unreachable because nothing calls `enterAgentActive()` in production — the hook checks `broker.getCurrentState() === "agent-active"` but the gate no longer drives that transition (confirmed). The `draining` state remains unreachable — no code path enters it (confirmed). Tool `holdMs` still accepts any value below the config minimum without bounds checking (confirmed, low severity).

**Verdict**: NEEDS_CHANGES

## High-level view

The v1 fix removed `enterAgentActive()` from the gate, which is correct. But warmup recalibration in `index.ts` still guards on `broker.getCurrentState() === "agent-active"` — a state unreachable in production. Recalibration never fires, so the first loaded model will spike VRAM above baseline and trigger a false ghost-claim.

The `draining` state exists in the type union and `canAgentRun()` but has no entry path. Ghost-claims jump directly to `user-claimed`. Unreachable code with an unreachable test branch.

## Warmup recalibration unreachable after gate fix

The v1 review flagged that the gate called `enterAgentActive()` and the broker never returned to idle. The fix correctly removed the state transition from the gate — but the warmup path in `index.ts` still depends on it:

```typescript
api.on("before_model_resolve", async (_event, _ctx) => {
  const result = runGate();
  if (!warmupDone && broker.getCurrentState() === "agent-active") {
    warmupDone = true;
    await recalibrateAfterWarmup(broker, api.logger);
  }
  return result ?? {};
});
```

Since `enterAgentActive()` is never called outside tests, `getCurrentState()` returns `"idle"` on every hook invocation. The `warmupDone` flag never flips, and `recalibrateAfterWarmup` never runs. The first model loaded after startup will spike VRAM above baseline and trigger a ghost-claim that could have been avoided by recalibration.

The simplest fix: remove the state guard and recalibrate on the first permitted gate call:

```typescript
if (!warmupDone && runGate() === undefined) {
  warmupDone = true;
  await recalibrateAfterWarmup(broker, api.logger);
}
```

Or call `broker.enterAgentActive()` explicitly in the hook if the agent-active state serves other purposes.

## Unreachable `draining` state

The state machine type defines five states but only four are reachable: `idle`, `agent-active` (via direct `enterAgentActive()` call in tests), `user-claimed` (via `claim()` or ghost-claim), and `dormant` (via config). The `draining` state has a case in `canAgentRun()` and the `claim()` rejection guard, but no transition ever enters it. Ghost-claims jump directly from `idle`/`agent-active` to `user-claimed`.

This is likely a placeholder for a future evacuation-then-release flow (e.g., unload models, wait for VRAM to clear, then mark as `user-claimed`). Not blocking, but the unreachable code adds cognitive overhead.

## Tool holdMs validation

The config enforces `defaultHoldMs >= 1000` via `resolveConfig()`, but tool-provided `holdMs` bypasses this. `broker.claim(holdMs)` directly passes the value to `setTimeout`. A call like `gpu.release({holdMs: 1})` creates a lease that auto-expires in 1ms — before the tool response can be returned to the agent. Since tools are invoked by agents (not untrusted external input), exploitation risk is minimal, but the asymmetry between config validation and runtime validation is surprising.
