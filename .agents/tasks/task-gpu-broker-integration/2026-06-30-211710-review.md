# GPU Broker: VRAM arbitration plugin for OpenClaw

A new extension plugin implements a five-state state machine (idle, agent-active, user-claimed, draining, dormant) that arbitrates GPU VRAM between agent inference and user workloads. The broker polls nvidia-smi or Ollama's `/api/ps` endpoint, detects external VRAM pressure via ghost-claims, supports explicit lease-based claims with auto-expiry, and gates agent model requests through the `before_model_resolve` hook. The plugin follows OpenClaw conventions: `definePluginEntry`, typed `api.on`, service lifecycle, and operator surfaces (HTTP, CLI, Control UI).

**Watch for:** The `reload.onConfigChange` field doesn't match the `OpenClawPluginReloadRegistration` type (confirmed — it has `restartPrefixes`/`hotPrefixes`/`noopPrefixes`, not `onConfigChange`). The run gate never transitions the broker _back_ from `agent-active` to `idle`, so the state ratchets forward on first permitted run and stays there indefinitely (confirmed). The `before_model_resolve` hook handler ignores the `(event, ctx)` parameters expected by the typed hook signature (confirmed — functionally harmless but blocks TypeScript strict compilation).

## High-level view

The `reload` field on the plugin entry uses `onConfigChange(api)` — a method that doesn't exist on the `OpenClawPluginReloadRegistration` type. The runtime will silently ignore it. The broker reference is stored by monkeypatching `api` with a `__gpuBroker` property, which is fragile but only reachable through this dead path today.

The run gate hooks into `before_model_resolve` and calls `broker.enterAgentActive()` on the first permitted run. Nothing ever calls `exitAgentActive()`, so the broker enters `agent-active` and never returns to `idle` during the session. Ghost-claim detection still works (it fires in both idle and agent-active), but any logic that distinguishes the two states is unreachable after the first inference call.

The Ollama snapshot fallback reports `totalMb: 0` and `freeMb: 0` since Ollama doesn't expose total GPU capacity. Any consumer relying on those fields for percentage or headroom calculations will get misleading data via the `/gpu/state` route or `gpu.status` tool.

The `draining` state is defined in the type union but never entered by any code path in this diff. If a ghost-claim triggers during `agent-active`, the state jumps directly to `user-claimed` without passing through `draining`.

<summary>Issues (5)</summary>

1. **`reload.onConfigChange` is dead code** — `OpenClawPluginReloadRegistration` type defines `restartPrefixes`/`hotPrefixes`/`noopPrefixes`, not `onConfigChange`. Either use `api.registerReload({ hotPrefixes: [...] })` and handle config change inside the service, or extend the reload contract if this is a planned SDK addition.
2. **`agent-active` state never exits** — `enterAgentActive()` is called on first gate permit but `exitAgentActive()` is never wired to any hook or lifecycle event. Add a transition back to idle (e.g. after agent turn ends or on a timer) or remove the idle→agent-active distinction if it serves no behavioral purpose.
3. **Hook handler arity mismatch** — The `before_model_resolve` handler is registered as `async () => { ... }` but the typed signature expects `(event, ctx)`. TypeScript strict mode will reject this. Accept the parameters even if unused: `async (_event, _ctx) => { ... }`.
4. **Ollama snapshot returns `totalMb: 0, freeMb: 0`** — Any downstream consumer using `totalMb` for percentage calculations or `freeMb` for headroom checks will get divide-by-zero or misleading results. Consider omitting those fields or marking the snapshot as partial.
5. **Run gate cannot actually block agent runs** — The gate logs a warning when denied but returns `undefined` (no override). This is documented in code comments and is a known limitation of `before_model_resolve`, but it means the broker's claim/deny semantics are advisory only. If true enforcement is needed, a different hook point or a provider-level gate would be required.

## Reload contract mismatch

The `OpenClawPluginReloadRegistration` type in `src/plugins/types.ts`:

```typescript
export type OpenClawPluginReloadRegistration = {
  restartPrefixes?: string[];
  hotPrefixes?: string[];
  noopPrefixes?: string[];
};
```

The gpu-broker passes `{ onConfigChange(api) { ... } }` as the `reload` field. This satisfies structural typing (all fields optional, extra properties pass without `exactOptionalPropertyTypes`), but the plugin loader never calls `onConfigChange` — it only reads the prefix arrays to decide reload behavior. The well-implemented `applyConfig` method on the broker is unreachable in production.

## State ratchet: idle → agent-active with no return path

After the first inference call, the broker sits in `agent-active` permanently. Consequences:

- The warmup recalibration fires exactly once (gated by `!warmupDone && state === "agent-active"`), which appears intentional.
- Any future logic needing to distinguish "agent is actively using GPU" from "agent finished and GPU is free" has no signal.
- The `exitAgentActive()` method exists but is dead code outside tests.

## Unreachable `draining` state and ghost-claim behavior

Ghost-claim uses threshold/half-threshold hysteresis — triggers when `usedMb - baselineUsedMb > externalClaimThresholdMb`, auto-releases when pressure drops below half. If a ghost-claim triggers during `agent-active`, the state jumps to `user-claimed` directly. The `draining` state exists in the union type as a future placeholder but has no entry path.

## Ollama snapshot partial data

When nvidia-smi is unavailable, the Ollama path produces:

```typescript
return { totalMb: 0, usedMb, freeMb: 0, timestamp: Date.now() };
```

The `GpuSnapshot` type doesn't distinguish "unknown" from "zero". The broker's ghost-claim logic only uses `usedMb` relative to baseline, so internal calculations are safe. Exposing this via `/gpu/state` or `gpu.status` means operators see `totalMb: 0` with no indication that total capacity is simply unknown rather than zero.

## Tool `holdMs` validation gap

`gpu.release` and `gpu.handoff` accept any `holdMs` value without bounds checking. The broker config enforces `defaultHoldMs >= 1000` but direct `claim(holdMs)` calls accept values like 1ms, which would expire before the response reaches the caller. Low-severity since tools are invoked by agents, not untrusted input.
